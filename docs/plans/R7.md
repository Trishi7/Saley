## 1. Scope
**In:**
- One card per dashboard notification, for every card type M1–M15, A1, A2 (docs/09 §5), with the look of the mock and the voice of docs/12b.
- The worker plans the cards (`cards_plan`), the caps order them, the bot delivers them, hears the presses, and edits the card in place.
- One SQL door for a press, `saley_card_press`. It maps each action to an existing door. Writers come from `DISCORD_WRITE_IDS` and are checked in SQL.
- Card sync: a dashboard act or an undo edits the Discord card within 5 s (`NOTIFY saley_card`).
- Modals (M5 note, M6 after the meeting, M8 move date, M14 answer) and select menus (M3, M11, name collision).
- Deep links into the dashboard; the dashboard scrolls to the item and outlines it; sign-in keeps a same-site `next`.
- Chat memory: capture, a 14-day backfill once, a nightly summary and facts, 90 days retention, `saley chat forget`.
- Answers: an intent step in the worker (LLM_SMALL, fixed schema, 10 s) in front of the R4 grammar; chat memory as a source; a private thread for long answers.
- Health: the M15 embed, a Discord block on Sources & health, `saley bot status`.
- Live round trips for every card type in the test channel.

**Out (brief):**
- Email drafts and sending (D258). The R4 action card stays for proposals that are not email.
- The API Sales cut-over and stopping the v1 `sales-bot`.
- DMs on (`DM_ENABLED` stays false). Apollo "Find people" (a disabled button only).

## 3. Design

### 3.1 One card per dashboard notification (D259)
- A "dashboard notification" is an item that the dashboard already shows: a Today task (meeting, reconnect), a Needs-a-look signal, an open proposal, a commitment reminder, an event, a new account, an open `ask`, the pack, the blockers, the health line.
- `card_id` is the key of that item (`m5-c412-2026-10-24`, `m10-p12`). It is unique in `bot_post`, so `insert … on conflict do nothing` is the "one card" rule. The deep link carries the same id.
- The worker renders the card. `bot_post.payload` holds the Discord message body (embeds or Components v2, buttons) and `rendered_hash`. The bot never builds card text.
- `bot_post.payload.keys` lists the items of the card (`proposal:12`, `contact:412`, `commitment:9`). The sync trigger finds a card by these keys.

### 3.2 Renderers (`bot/cards/`, `bot/components.py`)
- Pure functions: `render(rows, ctx) -> dict`. Values come from the rows only. `ctx` holds `public_url`, the card id and the time.
- `components.py`: `LIST_MAX` (= `BOT_LIST_MAX`, 5), `BUTTONS_MAX` 4, a select menu when a card has more choices, the closing line (docs/12b rule 4), the colours (docs/09 §9), the link text rule (never Open/View/Click).
- Overflow: items over `BOT_LIST_MAX` go into `payload.thread` (one post, same order). The bot posts it in a public thread under the card.
- Button `custom_id`: `c7:<card_id>:<action>[:<arg>]` (at most 100 characters). A `DynamicItem` hears it, so a press works after a restart (as D129).

### 3.3 Press path (`bot/press.py`, `saley_card_press`)
- `saley_card_press(p_card_id, p_user, p_action, p_payload, p_surface)` returns `{result: ok|already|refused|error, code, by, at, write_id, undo_until}` and writes one `bot_interaction` row for every call.
- Writer check: `users.discord_writer` (true for the short names in `DISCORD_WRITE_IDS`; the bot sets it at start, as it sets `discord_id`). The bot checks first, the SQL check counts (D257). Read-only presses need no writer: Seen it, Not useful, Skip on M3, More, Dismiss, Ask Sid/Vaishnavi, and Answer on M14 by the person who was asked.
- Map (the door does the write; `saley_card_press` only maps):

| Card · action | Door |
| --- | --- |
| M2 seen, not_useful | `saley_mark_seen` (story) |
| M3 do (select) · M10 yes / not_yet · R4 card | `saley_proposal_resolve` do / skip |
| M6 no_show, status (modal) · M10 li | `saley_act` write `meeting_status` |
| M6 next step + date (modal) | a `commitment` row for the presser, source `discord` |
| M7 done | `saley_act` task_done `reconnect` |
| M8 done | `saley_commitment_done` |
| M8 move date (modal) | `commitment.due` for an open commitment of the presser |
| M7 move a week · M9 snooze a day | a copy of the card, due later (`<card_id>-later-<date>`) |
| M5 note · M4 interest · M11 take · M14 answer | a `fact` row (`source_type` `discord`; M14 `teammate`), the ask answered |
| undo | `saley_undo_group` |

- After the call the bot edits the card: buttons go, the footer says `Done by Sid in Discord at 11:24 · Undo 4 min left`. An ephemeral reply only on `already`, `refused` and `error`.

### 3.4 Sync (`bot/sync.py`)
- 0027 trigger on `decision` insert and on `undone_at` update: `pg_notify('saley_card', card_id)` for every sent card whose `payload.keys` holds an item of the decision (proposal, contact by row key, commitment).
- The bot LISTENs on its own psycopg connection in a thread. On a notify it reads `v_bot_card` and edits the message (footer "on the dashboard", buttons off; undo puts them back). On reconnect it re-reads cards changed in the last 10 minutes.

### 3.5 Answers (F-R7-09)
- The bot has no LLM key (docs/17 §3). It writes an `answer_intent` row. The worker job `answer_intent` (every 2 s, quiet) asks LLM_SMALL inside a DATA block for `{kind, company, person, window, topic}` and parses it to that fixed schema. The bot polls the row for at most `BOT_INTENT_TIMEOUT_S`; then it uses the R4 grammar. With no LLM key the worker answers `none` at once.
- A known intent maps to a `Parsed` of the R4 engine. New intent `chat`: lines from `chat_message` of this channel (90 days) with `[Vaishnavi, Tue 12:40]`.
- `intel.guard` checks every line. Over `ANSWER_THREAD_LINES`: 3 lines in the channel, the rest in a private thread with the asker.
- Personal data (phone, personal email) never goes to a channel: `core.redact` removes it from channel answers.

### 3.6 Chat memory (F-R7-08)
- Every message in the chat channels (`CHAT_CHANNEL_IDS`; empty = test + sales) goes to `chat_message` (author short, time, text, reply-to, thread). Text only.
- Backfill once at start: `CHAT_BACKFILL_DAYS` of each channel, 100 a page; the key `chat_backfill_done` in `job_runs` stops a second run.
- Nightly `chat_summary` job (worker, LLM_MID): one call per channel-day, messages in DATA blocks; output parsed to `{summary, facts:[{company, person, text, message_id}]}`; facts with a company or person that is not in the input are dropped.
- Retention: the same job deletes `chat_message` older than `CHAT_RETENTION_DAYS`. `saley chat forget <message_id>` removes one line and its facts.

### 3.7 Deep links (F-R7-07)
- `bot/links.py`: `PUBLIC_URL/<page>/<id>?card=<card_id>`; the page set is fixed (today, people, accounts, pack, commitments, suggestions, events, signals, goals, health).
- The dashboard reads `?card=`, scrolls to `[data-card="<id>"]` and outlines it for 3 s. Sign-in keeps `next` when it is a same-site path.

### 3.8 Migrations
- 0027: `bot_post` + `card_type`, `priority`, `held_reason`, `discord_message_id`, `thread_id`, `card_id` (unique), `payload`, `rendered_hash`, `pinned`, `edited_at`; state `gone`; `bot_interaction`; `users.discord_writer`; `saley_card_press`; the trigger.
- 0028: `chat_message`, `chat_summary`, `chat_fact`, `discord_event_link`, `answer_intent`; views `v_bot_card`, `v_chat_recent` for saley_ro.
- Owner model D256: saley_admin owns the tables; the new SECURITY DEFINER function goes to `saley` (grants.sql list); PUBLIC revoked.
