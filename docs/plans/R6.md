## 3. Design

### 3.1 Compose (D243)
- App services carry `profiles: ["prod"]`. `postgres` has no profile and publishes no port.
- `migrate` runs `saley db-upgrade` with `DATABASE_URL_ADMIN`. `web`, `worker`, `bot` and `news` wait for it (`service_completed_successfully`).
- Each service gets only the database role it needs. Values set in `environment:` win over the env file. The web has no rw URL and no other secrets.
- Image `saley:${SALEY_TAG:-current}`. `deploy.sh` builds `saley:<sha>`, and tags it `current` only after the smoke passes.
- One external network `saley_net`. `install.sh` and `deploy.sh` create it when it is missing.
- `env_file: ${SALEY_ENV_FILE:-/srv/saley/.env}`. The service account key is mounted read-only from `/srv/saley/secrets/google-sa.json`.
- `deploy/compose.ci.yml` is the CI overlay. It sets `SALEY_ENV: ci` and mock sign-in, and publishes 8080 and 8443.

### 3.2 Settings (D242)
- `SALEY_ENV` is `dev`, `ci` or `prod`; any other value stops the process.
- In prod, `saley web` refuses to start when any of these is true:
  - `AUTH_PROVIDER=mock`, or google is not set up
  - `PUBLIC_URL` is not https
  - `GOOGLE_OAUTH_REDIRECT_URL` is not `PUBLIC_URL/auth/callback`
  - `WEB_SESSION_SECRET` is under 32 characters
- `ci` behaves like prod and allows mock sign-in. It works only when `PUBLIC_URL` is https://localhost or https://127.0.0.1.
- `SALEY_IN_CONTAINER` (the image sets it) turns off the busy-port check.

### 3.3 Roles (D244)
- `saley db-roles` connects as the `postgres` superuser, with `POSTGRES_PASSWORD`, to the host of `DATABASE_URL`.
- It creates or updates `saley_admin`, `saley` and `saley_ro` with the passwords in the three URLs. It creates the database when it is missing.
- It makes `saley_admin` a member of `saley`. Migrations then replace the functions that `saley` owns.
- Then it runs `src/saley/core/sql/grants.sql`. `deploy/sql/roles.sql` includes the same file (`\ir`), so the grants have one source.

### 3.4 Deploy and rollback (D248)
- `deploy.sh` takes a pre-deploy `pg_dump` before it migrates.
- Rollback puts back the previous image. The database stays, because migrations add and never remove.
- A schema rollback is "restore the pre-deploy backup" (runbook).

### 3.5 CI compose checks (D241, D247, D249, D251)
- `.github/workflows/compose.yml` runs on push to main and on `workflow_dispatch`. One matrix row is one named step (`R6-C02 …`).
- `verify.py --ci` reads the job steps of that workflow for HEAD over the public GitHub API and saves `docs/test-reports/R6-compose.json`. A row of tool `ci` passes when its step concluded `success`.
- The gate refuses the CI result when the tree differs from HEAD in a deploy path. The human commits and pushes first.
- No sheet credentials in CI:
  - `saley sync --raw-file` and `saley sheet verify --raw-file` read a sample sheet built from the test factory. Both refuse in prod.
  - The backup → restore → verify path is the real code.
- The browser smoke through caddy opens every view, with zero console errors and the CSP intact. The full browser QA stays at gate step 8 on the laptop.

### 3.6 Health (D245) and the lock heartbeat (D246)
- Health checks:
  - worker and news: a scheduler job touches `/tmp/saley-alive/<service>` every 30 s
  - bot: a loop touches the file while the gateway is ready
  - `python -m saley.core.alive <service>` (the small form of `saley alive`) is the health command
- Lock heartbeat: `run_job` renews the job lock every 5 min while the job runs. A lost lock logs `job_lock_lost`.

### 3.7 Migrations
- 0025: the topic check takes Opportunity; non-paper topics go back to null.
- 0026: a partial index `ix_decision_act_txid` on `decision (act_txid) where act_txid is not null`.

## 8. Risks
- The build on a 4 GB droplet: the Node stage needs about 1 GB. Swap covers it.
- PM2 apps share the RAM. The limits add up to 2.1 GB.
- Caddy needs ports 80 and 443 free and DNS pointing at the droplet before the first certificate.
- A deploy that migrates and then rolls back leaves the newer schema with the older code (D248).
